# mcp-entropia 设计记 —— 13 种概率分布是怎么定下来的

> 这是作坊里唯一一件**从零开始、没改过架构**的成员。它的设计过程很短，但每个决定背后
> 都有一个明确的问题。

## 缘起：一件具体的事

需求不是"我想要个随机数工具"，而是——**帮人核查一套卡方分布的数据**。

这个场景很关键，因为它决定了工具的形状：不是"给我一个随机数"这么随意，而是
"我要**按指定分布**采样，样本量要够，还要能验证"。所以 `chi_squared` 不是可有可无的
补充，它是**第一需求**。

## 它修补的缺陷

LLM 说"我给你生成一个随机数"时，它做的其实是 token 采样——输出的是**概率最高**的那个
"看起来随机"的数字。结果就是它反复吐 42、7、以及训练集里的常见模式，而且对"这是哪个
分布的样本"完全没有概念。

真正需要的是**按统计规律**产生的数：正态的是正态的、指数的是指数的、卡方的是卡方的。
这需要的是随机数发生器 + 分布变换，不是语言模型的下一 token 预测。

## 第一条设计决定：先说清它**不是**什么

工具描述的第一句就是：

> ⚠️ **NOT a CSPRNG**（非密码学安全随机数生成器）

所有分布用 Python stdlib `random`（Mersenne Twister）或 NumPy 的 PCG-64——它们是
**统计随机**，不是**密码学安全**。密钥、密码盐值、安全令牌请走 `secrets` 模块或 OS 级熵源。

这条是**用户明确要求写进文档**的。理由很实在：一个"能生成看起来随机的字节"的工具，
如果不说清它不能干密码学的活，早晚有人拿它生成密钥。**把边界写在最显眼处，是防误用，
不是免责。**

（CSPRNG 工具留作以后扩展——当时明确决定"暂时不做"。）

## 技术选型：stdlib 还是 numpy？—— 两个都要

最初的庙算倾向于"只用 stdlib `random`，零依赖"：

| 维度 | `random`（stdlib） | `numpy.random` |
|------|-------------------|----------------|
| 依赖 | 零 | numpy |
| 分布数 | 9 种 | 30+ |
| 性能 | 足够（MCP 调用粒度不是瓶颈） | 快但在这个场景下无意义 |

但卡方分布的核查需求把 `chi_squared` 变成了刚需，而 stdlib **没有**卡方。最终决定：
**两套都上**——

- stdlib 的 9 种分布（零依赖，立即可用）；
- numpy 里**使用频率最高**的 3 种（`binomial` / `poisson` / `chi_squared`），作为**可选依赖**。

代价是 numpy 三个工具在没装 numpy 时会返回一条明确的错误（`"NumPy 未安装…"`），而不是
假装能用。这不是降级，是**显式的缺口声明**。

## 工具粒度：一个分布一个 MCP tool

参照了同目录下 `cloakbrowser_fetch.py` 的"单工具"写法，但这里反过来——**13 个独立工具**，
每个分布一个。

理由写在设计里：MCP 的每个工具都有自己独立的 `inputSchema`，AI 调用时能**自然选对工具**，
不需要在一个巨型 schema 里做条件必填（"如果是正态就填 mu/sigma，如果是二项就填 n/p…"）。
用 13 个小而清晰的 schema，替代 1 个大而模糊的 schema。

## 最终的 13 个工具

**stdlib（零依赖，立即可用）：**

| 工具 | 分布 | 参数 |
|---|---|---|
| `uniform` | Uniform(0,1) | — |
| `std_normal` | N(0,1) | — |
| `uniform_range` | U(a,b) | a, b |
| `normal` | N(μ,σ) | mu, sigma |
| `bernoulli` | Bernoulli(p) → {0,1} | p |
| `exponential` | Exp(λ) | lambd |
| `gamma` | Gamma(α,β) | alpha, beta |
| `beta` | Beta(α,β) → (0,1) | alpha, beta |
| `lognormal` | LogNormal(μ,σ) | mu, sigma |
| `randint` | 离散均匀 [a,b] | a, b |

**numpy（可选依赖）：**

| 工具 | 分布 | 参数 |
|---|---|---|
| `binomial` | Binomial(n_trials, p) | n_trials, p |
| `poisson` | Poisson(λ) | lam |
| `chi_squared` | χ²(k) | k |

## 返回值设计：不只是个数字

每个工具返回一个 JSON 字符串，**带元数据**：

```json
{"distribution": "normal", "parameters": {"mu": 0, "sigma": 1}, "values": [-0.4237]}
```

这样 AI 拿到的不是一个裸数字，而是"**哪个分布、什么参数、采出来的值**"三件套——
可追溯、可复核。单值用 `value`，多值用 `values` 数组。

## 多值采样：把 n 个样本摊到一次调用

每个工具都有一个可选参数 `n=1`。一次 MCP round-trip 的开销摊到 n 个样本上，比调 n 次
便宜得多。

但 `n` **上限设为 10000**——不是技术限制，是**防滥用**：MCP 不是拿来跑大规模 Monte
Carlo 的，真有这种需求出门左转专业程序。上限是一道礼貌的边界。

## 几个刻意的取舍

1. **`randint` 单列成一个工具**，没有并进 `uniform_range` 加个 `integer=true` 开关。
   理由是"免得无法区分"——连着采样时，浮点和整数混在一起会让下游代码难处理。
2. **不做 CSPRNG**——以后有需要再扩展，不在第一版掺进来制造复杂度。
3. **numpy 是可选依赖**，缺席时只丢 3 个分布，其余 10 个照常。
4. **参数校验显式报错**，不静默修正。例如 `randint(a=10, b=5)` 返回
   `{"error": "a 必须 <= b，收到: a=10, b=5", "distribution": "randint"}`，
   而不是悄悄交换两个参数。

## 验收

上线后 13 个工具逐一采样验证，**13/13 全通过**（含边界错误：`randint(10,5)`、
`chi_squared(0)` 都正确报错）。

## 一句话

**LLM 不该"假装"生成随机数——真随机需要熵源，按分布采样需要分布变换。**
这个工具把这两件事交给会做的人（stdlib / numpy），LLM 只负责调用。
